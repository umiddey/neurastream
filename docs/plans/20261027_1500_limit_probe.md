# Main comes back within 5 minutes of its limit lifting, not up to an hour later
Worktree: /home/ukd/Work/neurastream-limit-probe
Branch: fix/limit-probe
Summary: When Main hits its provider limit, a tiny separate check runs every 5 minutes. Main restarts as soon as that check gets through, or exactly at the reset time when the error message names one. You get one ping when Main stops and one when it is back.

## Goal
- Owner (2026-10-27 ~14:10): "are there any scripts btw for how the agent knows when the limits are reset? btw that is currently broken … if you look at the logs from last night to 6am today, you will know it is broken … maybe we need to run a background process that runs every 5 minutes once the limits are hit for Main and once it is back, the Main resumes".
- Done = (1) a rate-limited Main turn end starts a probe loop: every `rate_limit.probe_interval_s` (default 300) one tiny request (`rate_limit.probe_cmd`, with timeout) goes to Main's provider+model; (2) the first successful probe resumes Main within one adapter tick (≤ 30 s); (3) when the error text names a reset time (zai "reset at … (= … CET local)", codex/cursor dates) Main waits until it + slack and does not probe before; (4) no exponential growth to 60 min; (5) while limited only the probe touches the provider, never a full-context Main turn; (6) the owner gets ONE "Main limited" and ONE "Main back" post per episode; (7) Main's chat shows the limit error ONCE per episode (owner 2026-10-27 ~14:25: "I don't want the error to be shown on the main chat message again and again … the first time we get a rate limit is the only time … in the background we run that every five minutes … once we hit no longer rate limit, the main is properly triggered again"): probes run in the background, their failures never reach Main's chat, and Main gets a new turn only after a probe succeeds; (8) each episode is recorded as a metric so the feedback-loop report shows limited minutes.
