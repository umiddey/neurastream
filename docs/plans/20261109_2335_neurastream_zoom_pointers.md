Summary: Every owner message and every Main answer is kept word for word, forever, in one append-only log. `neurastream recall <words>` finds an old question or decision and prints it exactly as it was said. On top of it, a topic index (one short pointer line per conversation segment, written by a cheap model in the background) narrows a search down to the right stretch of the raw log; the raw message stays the only truth, and nothing from either layer is added to Main's prompt.

- Done means:
  - Every owner message and every Main turn-end answer is appended, word for word and secret-redacted, to `<queue_state>/recall/owner-log.jsonl` (dir mode 0700, file mode 0600). The file is never trimmed or rewritten.
  - `neurastream recall <words>` lists the matching entries, newest first, each with an id, a date, who said it and a short preview.
  - `neurastream recall --show <id>` prints that owner message whole and Main's answer to it whole.
  - `neurastream recall backfill` fills the log once from the session files already on disk, with no model call.
  - Main's rules carry one line telling it to run `neurastream recall` when the owner asks about something from the past.
  - P6-P11: `<queue_state>/recall/owner-topics.jsonl` holds one line per conversation segment (one subject, 3-60 log entries): its id range, a title, keywords including the owner's exact phrases, decisions and owner questions as one-line pointers carrying the entry id, names (paths, plans, agents, numbers, dates) and a `continues` link to an earlier segment on the same subject. About 60 words per segment. It is an index only: no reasoning, tool output, status chatter or judgment, and nothing in it ever enters Main's prompt.
  - `neurastream recall <words>` searches the topic index first and lists the matching segments with their ranges, then the raw entries inside those ranges, then the other raw hits; `neurastream recall --show <from>..<to>` prints a range word for word. With the index off, missing, unreadable, or a stretch left unindexed, the raw word search answers exactly as in P2.
  - A cheap model reached through the harness's own logins cuts the segments: once over the backfilled history, then in a detached background run after every `recall.topics_every` new entries and at Main's session end. No run ever blocks a turn. An answer that fails the code checks twice leaves its stretch unindexed.
  - `recall.topics_every` is set from the backfill's numbers (P11); until then it stays at its provisional default.

## Background
- **Why not the tree:** the view is a map made of model-written summaries. It costs tokens on every request and a line can be wrong. The owner left OptChat on Oct 10 because a summary dropped a goal. Here the raw log stores only the exact text; the P6-P11 topic index adds pointer lines that are never put in Main's prompt and only lead back to that text (see "Two layers").
- **Why not just raise the 50 + 20 limit:** that file is rewritten whole on every message and its readers want only the last day. A separate append-only file keeps both simple.
- **What is logged:** the owner's messages (typed or from the phone page) that pass `isOwnerProse` (src/core/guards.ts:501 in the worktree), cut to the owner part by `ownerText` (src/core/rollover.ts:134-142), and the text Main ends a turn with, both redacted before the write. Tool output, thinking, guard lines and subagent results are not logged; they stay in the session files.
- **Size:** about 400-800 owner messages a week (weekly report M4), each with one answer of a few KB at most. That is a few MB a month, searched with a plain file scan.
- **Accepted limit:** Main does not notice an old decision by itself; it searches when the owner asks or refers to the past. If that proves too weak, a small view can be added later on top of this same log.
- **Several Mains:** all Mains append to the one log in `<queue_state>/recall/`. Lines are appended whole, so they interleave by time. Each line carries its own random-suffixed id (P2 `newEntryId`), so no writer counts lines or takes a lock, and two writers cannot hand out the same id except at 2^-32 odds within one millisecond.
- **Why a log when the session files keep everything (review F9):** they are not lossy today. omp compaction appends a `"type":"compaction"` line and keeps the earlier lines (largest Main file: 69 compaction lines, every earlier user line still there), rollover starts a new file and keeps the old one, and neurastream never deletes a session file; on 2026-11-13 all 211 Main files back to 2026-08-15 were present (547 MB, 3.2 GB with subagent dirs). The log still earns its keep: it is redacted (the session files hold owner prompts and Main replies raw; the adapter redacts only tool results, src/adapters/omp/index.ts:347-355), it is one harness-neutral file of a few MB that a plain scan searches instead of parsing 211 harness files, and it survives whatever session cleanup or format change a harness makes, which neurastream does not control. The backfill reads the session files once to fill the history.
- **Modes:** the log lives in its own `recall/` subdir at 0700 with files at 0600, because the shared queue state dir is 0755 and chmodding it would change every other state file's dir. The old `owner-messages.jsonl` (0644, unredacted) is left as it is.
- **Two layers:** layer 1 is the raw log (P1-P5), the only truth. Layer 2, `owner-topics.jsonl`, only points: a search hits a title, keyword, name or pointer line, and the answer is read from the raw range it names. A pointer line can be wrong; the raw text it leads to cannot. Neither layer is put in Main's prompt.
- **Replace rule:** each run re-cuts the still-open last segment, so it appends lines starting at that segment's `from`. Reading the topics file top to bottom, a line starting at X drops every earlier line starting at X or at an entry after X in log order (oldest first, the reverse of `readEntries()`). Appends only, and a half-done run leaves at most a half line, which readers skip.
- **Unindexed stretches:** an answer that fails the checks twice gets one `skipped` line for its new entries, so the next run moves on instead of retrying forever. Raw word search still finds those entries.
- **Why the auth gateway, not print mode or an API call:** the machine has OAuth logins for anthropic and zai and no API key for either; reading omp's tokens from neurastream is forbidden (AGENTS.md: keyrings, secrets). `omp auth-gateway stdio` answers one OpenAI-style chat request per stdin line with those logins and runs no agent loop, so a request without a `tools` key gives the model nothing to call. Measured 2026-11-13 with `anthropic/claude-haiku-5-5` from an empty temp cwd: a request asking the model to read /etc/hostname with a tool, or answer `NO-TOOL`, used 78 prompt tokens and answered `NO-TOOL`, with no `tool_calls` (the file holds `ukd`); a system+user request used 55 prompt tokens and reported 0 callable tools. Print mode was dropped: `omp -p --no-tools` (same empty cwd, `zai/glm-5.3-flash`) still started the configured MCP servers (6 connect-failure warnings) and warned that "the system prompt and always-sent tool schemas alone exceed the recovery band", and the earlier `--tools=read` setup leaves a file reader the model can point at any path.
- **Batch size:** 45 new entries plus the open segment per call (measured median 22.5k chars, about 16k input tokens with print mode's fixed part on haiku; through the gateway the fixed part is only the system prompt, so less). The trigger count `recall.topics_every` defaults to 30 only until P11 sets it from the backfill's entries per topic; the sample batch gave about 5.6 entries per segment.
- **Model egress:** owner text reaches the model provider only after redaction. The topic run reads only the redacted log (P2, P3 redact before every write), so each request carries text that `recordOwnerLog` already passed through `redactSecrets`; Main already sends that text to its own provider, so this adds a provider, not a new exposure class.
