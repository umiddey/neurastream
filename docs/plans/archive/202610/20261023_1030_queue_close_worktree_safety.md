# neurastream: queue-close must judge the real main branch and never remove a worktree that holds other work
Worktree: /home/ukd/Work/neurastream-qclose

## Goal
- Owner (2026-10-22 23:0x): "find bugs in your own system … and when you find them in real time write up plan and start improving". Three queue-close bugs hit Main on 2026-10-23 while closing `20261022_1500_amiiir_feedback_fixes.md` (CP repo):
  1. Wrong base. `base` = `refs/remotes/origin/HEAD` of `plan.repo` (`src/core/queue-close.ts` ~line 97). The CP checkout's `origin` is a local clone (`/home/ukd/Work/cp-mr98`), so origin/HEAD was that clone's checked-out branch (`chore/gateforge-0.10.0`), and its `main` was stale. Result: "AWAITING merge" for a branch already merged on GitLab main.
  2. Removed a worktree that held other work. The plan's `Worktree:` (Work/cp-letterhead, since deleted) had since been reused for another branch (`fix/customer-uuid-fields`, MR !135). queue-close ran `git worktree remove --force` on it anyway. That half-deleted it: `.git` was gone, root-owned `frontend/.vite/deps_temp_*` stayed, and the error was "Directory not empty", which the `/Permission denied/` retry (~line 158) does not match.
  3. Done check run in the wrong tree. Once the worktree was gone, `runIn = plan.repo` (~line 109), a checkout on an old branch. The check failed, and queue-close wrote `Status: open` (reopened) for work that is on main.
- When done, these hold:
  - (a) The merged test uses the upstream's real default branch. When `origin` is a local path, follow it to that repo's own `origin` (at most 3 hops) and test against the upstream's default ref there (fetch it first). A branch on GitLab main counts as merged even when the clone's HEAD is a feature branch.
  - (b) queue-close removes the plan's worktree only when that worktree's checked-out branch is the plan's `Branch:` (or detached at a commit reachable from it). Otherwise it prints `queue-close: worktree <p> kept: it is on <other branch>`. It does not stash or remove it, does not delete a branch checked out there, and goes on to archive the plan.
  - (c) If `git worktree remove --force` fails for any reason and the path still exists, it chowns via the existing docker step, removes the directory and prunes. That covers "Directory not empty" and not just "Permission denied". This only runs after (b) said the worktree is the plan's.
  - (d) When the worktree is missing or was kept by (b), the done check runs in a fresh detached worktree of the base from (a), under the queue state dir, removed afterwards. It never runs in `plan.repo`'s current checkout. A failure there still reopens the plan, as today.
